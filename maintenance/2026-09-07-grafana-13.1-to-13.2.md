# 2026-09-07 — Grafana 13.1.0 → 13.2.1

Git had said `grafana/grafana:13.2.1` since the bulk tag bump in `f86d8f1`, but the cluster
had never been given it — the pod was still running 13.1.0. This closes that gap.

A Grafana minor migrates its SQLite database **in place and one-way**: 13.2.1 adds tables and
columns that 13.1.0 does not understand, so there is no going back to the old image on the
same file. `grafana-data` is also `numberOfReplicas: 1` (see
[`../arm64-srv/k8s/monitoring/README.md`](../arm64-srv/k8s/monitoring/README.md), "Where the
data lives"), so Longhorn holds no second copy to fall back on. That is why this was done
deliberately rather than as part of a routine tag bump.

## Order of operations, and why each step is where it is

1. **Pre-pull the new image on the target node, before touching anything.** The Deployment is
   `maxSurge: 0` / `maxUnavailable: 1`, forced by the RWO claim — two pods would mean two
   attach attempts, so the old pod is *terminated before* the new one starts. That inverts the
   usual rollout risk: an unpullable tag is not a failed rollout that leaves the old pod
   serving, it is an outage that lasts as long as the pull. Pull it first with a throwaway pod
   pinned to the same node and let it print its own version:

   ```bash
   kubectl -n monitoring run grafana-prepull --image=grafana/grafana:13.2.1 --restart=Never \
     --overrides='{"spec":{"nodeSelector":{"kubernetes.io/arch":"amd64"}}}' \
     --command -- sh -c 'grafana --version'
   ```

   It took just over four minutes to pull. Grafana served normally throughout, which is the
   entire point of doing it in this order — the roll itself was then pull-free and the pod was
   Ready 25s after the apply.

2. **Longhorn snapshot, while the volume is still attached.** Longhorn snapshots are taken by
   the live engine, so a detached volume cannot be snapshotted — this has to happen before the
   scale-down, not after. Note there is no CSI `VolumeSnapshot` in this cluster (no
   external-snapshotter); the native CRD is the only route:

   ```bash
   kubectl apply -f - <<'EOF'
   apiVersion: longhorn.io/v1beta2
   kind: Snapshot
   metadata: { name: grafana-data-pre-13-2-1, namespace: longhorn-system }
   spec: { volume: pvc-164f0164-9062-417b-8bf0-21e648477c20, createSnapshot: true }
   EOF
   ```

   This is crash-consistent, not application-consistent. SQLite is crash-safe, so it is a
   legitimate rollback point — but it lives on the same disk as the volume, so it is a fast
   revert, not a backup.

3. **Scale to 0 and copy the data off the volume.** This is the authoritative backup, and it
   is taken with the process stopped so SQLite is closed cleanly rather than copied live.
   Because the claim is RWO, the helper pod can only attach once grafana is gone, and it must
   be pinned to the same node as the volume's single replica:

   ```bash
   kubectl -n monitoring scale deploy grafana --replicas=0
   # helper pod: image grafana/grafana:13.2.1 (already local, has a shell), mounts
   # grafana-data readOnly at /data, runAsUser/fsGroup 472
   kubectl -n monitoring exec grafana-backup -- tar czf - -C /data . > grafana-data-13.1.0.tar.gz
   ```

   Verify the archive holds no `*-wal`, `*-journal` or `*-shm` file. Their absence is the
   proof the shutdown was clean and the copied database is consistent; if one is present, the
   copy is mid-transaction and should be retaken.

4. **Apply the single file, not the directory.** `grafana-ingress.yaml` lives in the same
   directory and its host is a placeholder — applying the directory would take Grafana off the
   internet at the exact moment you are trying to upgrade it. The manifest carries
   `replicas: 1`, so this also scales it back up:

   ```bash
   kubectl apply -f amd64-srv/k8s/monitoring/grafana/grafana-deployment.yaml
   ```

## What it did

13 migrations, 0 failures, no `level=error` lines, `/api/health` reporting
`{"database": "ok", "version": "13.2.1"}`, and HTTP 200 both from the ClusterIP service and
through `traefik-external` with the real Host header.

Data was verified by row count rather than by assuming, comparing the pre-upgrade copy with
the live database (`python3` has `sqlite3` in the standard library, and the Grafana image no
longer ships the `sqlite3` CLI — it uses the pure-Go `modernc.org/sqlite` driver):

| | before | after |
| --- | --- | --- |
| `pragma integrity_check` | ok | ok |
| `user` | 1 | 1 |
| `data_source` | 3 | 3 |
| `org` / `star` | 1 / 3 | 1 / 3 |
| tables | 88 | **92** |

The four new tables are the migration. Note `dashboard` is 0 both before and after: in this
version provisioned dashboards live in unified storage, not the legacy `dashboard` table, so
that zero is not data loss — the three `star` rows point at dashboards that resolve fine.

One pre-existing warning is unrelated to the upgrade and worth fixing sometime:

```
level=warn msg="SQLite database file has broader permissions than it should"
  path=/var/lib/grafana/grafana.db mode=-rw-rw---- expected=-rw-r-----
```

## Rolling back

Only if something surfaces later — the image cannot simply be reverted, because 13.1.0 will
not run on a database 13.2.1 has migrated. Restore the data first, then the tag:

```bash
kubectl -n monitoring scale deploy grafana --replicas=0
# option A, fastest: revert the Longhorn snapshot grafana-data-pre-13-2-1
#   (volume must be detached; use the Longhorn UI or the volume's revert action)
# option B: helper pod mounting grafana-data read-write, then
#   kubectl -n monitoring exec -i <helper> -- tar xzf - -C /data < grafana-data-13.1.0.tar.gz
kubectl -n monitoring set image deploy/grafana grafana=grafana/grafana:13.1.0
kubectl -n monitoring scale deploy grafana --replicas=1
```

Then revert the tag in `grafana-deployment.yaml` too, or the next apply undoes the rollback.

The snapshot and the tarball are both worth deleting once you are satisfied — the snapshot
takes space on dell's disk, which is the resource that forced monitoring onto one replica in
the first place.
