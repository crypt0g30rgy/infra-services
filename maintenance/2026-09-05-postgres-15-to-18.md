# PostgreSQL 15 → 18, all three servers — 2026-09-05

Every PostgreSQL 15 server in the cluster is now **18.6**. This was not a tag
bump: PostgreSQL refuses to start on a data directory written by an older major,
so each server was dumped, its volume emptied, and the dump restored into a fresh
18 cluster. Every row count, role, schema and sequence was compared before and
after and came out identical.

| Server | Kind | Database | Node | Before | After | Data verified |
|---|---|---|---|---|---|---|
| `xboy/postgres-root` | Deployment | `root_db` | amd64 | 15.19 | **18.6** | identical |
| `xboy/postgres-xboy` | Deployment | `blog_db` | amd64 | 15.19 | **18.6** | identical |
| `vaultwarden/postgres` | StatefulSet | `vaultwarden` | amd64 | 15.19 | **18.6** | identical |

`xboy/postgres-foodiehub` is on **16-alpine and was left alone** — it is a
different major, it was not in the reported update, and the procedure below
applies to it unchanged whenever it is worth doing.

Manifests, both repos:

- `xboy-k8s-infra` commit `efe3728` — `infrastructure/base/data/postgres-{root,xboy}/base/deployment.yaml`
- this repo — [`../arm64-srv/k8s/vault-warden/postgres-statefulset.yaml`](../arm64-srv/k8s/vault-warden/postgres-statefulset.yaml)

## Why dump and restore rather than `pg_upgrade`

`pg_upgrade` needs both the old and the new binaries in the same filesystem. The
`postgres:*-alpine` images ship exactly one major each, so using it would mean
building a custom image for a one-off migration. These databases are 2 KB, 11 KB
and 330 KB compressed; a dump and restore takes seconds and is the path with a
readable failure mode.

It also buys something `pg_upgrade` cannot: **`data_checksums` is on** in all
three servers now. 18 enables it by default at `initdb` time, and the only way to
get it on an existing cluster is to write a new one. Given that three Postgres
volumes on this cluster were corrupted earlier the same day, when a host-wide
memory collapse took the nodes down
([`../incidents/2026-09-05-microk8s-mass-pod-eviction.md`](../incidents/2026-09-05-microk8s-mass-pod-eviction.md)),
having the server detect a torn page instead of serving it is the point.

## Three independent safety nets, per server, before touching anything

1. **S3, through the CronJob that already exists** — not a hand-rolled copy, so
   the restore path being relied on is the one that is actually scheduled.
   `kubectl create job --from=cronjob/...`, then read the log for
   `UPLOAD_VERIFIED_OK` (it re-downloads the object and compares the checksum).
2. **A local `pg_dumpall | gzip`**, which is also the restore source. Verified
   structurally before use — `gzip -t`, and the `CREATE TABLE` count checked
   against the `COPY` count (29 and 29 for vaultwarden).
3. **A Longhorn snapshot of the volume**, which is the only one of the three that
   can put the *old cluster* back rather than the old data:

   ```yaml
   apiVersion: longhorn.io/v1beta2
   kind: Snapshot
   metadata: {name: pre-pg18-vaultwarden-20260905, namespace: longhorn-system}
   spec: {volume: pvc-8fb90215-bbfc-442f-9653-720544599698, createSnapshot: true}
   ```

   All three (`pre-pg18-{root,xboy,vaultwarden}-20260905`) are `readyToUse` and
   still on the volumes. They are snapshots, **not backups** — the Longhorn
   backup target is still empty, so they die with the volume. Delete them once
   18 has run for a while; until then they are the fastest rollback.

The `pg_dumpall` files contain role password hashes. They live in `/tmp/pgupg/`
at mode 600 on the workstation and are **not** in this repo, and `/tmp` does not
survive a reboot.

## The procedure, per server

Run it for **one server at a time**. See the first trap below for what happens
otherwise.

```bash
# 0. inventory + all three safety nets (above), then:
kubectl -n <ns> scale deploy/<consumer> --replicas=0      # stop writers first
kubectl -n <ns> scale deploy/<server>   --replicas=0      # or sts/<server>

# 1. empty the volume. A pod on the node the volume is on, mounting the PVC.
#    Keep lost+found: it belongs to the filesystem, not to Postgres.
kubectl apply -f wipe-<server>.yaml && kubectl -n <ns> logs pgupg-wipe-<server>

# 2. bring it up on 18 - it initdb's a fresh cluster
kubectl apply -f <the 18 manifest> && kubectl -n <ns> scale ... --replicas=1

# 3. the entrypoint has just created POSTGRES_DB empty. pg_dumpall's own
#    CREATE DATABASE will not run while it exists, so drop it.
kubectl -n <ns> exec <pod> -- sh -c \
  'psql -U "$POSTGRES_USER" -d postgres -c "DROP DATABASE IF EXISTS \"$POSTGRES_DB\";"'

# 4. restore (see the kubectl-exec-stdin trap for why via a file), verify,
#    VACUUM ANALYZE, then scale the consumer back up.
```

Expected noise during a `pg_dumpall` restore: exactly one
`ERROR: role "<POSTGRES_USER>" already exists`, because the entrypoint created
that role before the dump got to it. The dump's following `ALTER ROLE ... PASSWORD`
still applies, so the credential ends up as it was. **Any second error means
stop.**

## Traps, in the order they cost time

### 1. Applying two servers in one `kubectl apply` breaks the one you are not on

The rendered manifest had both xboy Deployments in it, and applying the file
moved `postgres-xboy` to 18 while its data directory was still 15:

```
FATAL:  database files are incompatible with server
DETAIL:  The data directory was initialized by PostgreSQL version 15,
         which is not compatible with this version 18.6.
```

Four restarts, and **no data damage** — 18 checks `PG_VERSION` and exits before
it opens anything, which is the one merciful thing about this failure. Recovery
was `kubectl set image deploy/postgres-xboy postgres=postgres:15-alpine`, and the
inventory afterwards was byte-identical to the pre-flight capture. Apply per
server, at the point in the sequence where *that* volume has already been wiped.

### 2. `postgres:18` changed the image's default `PGDATA`

18 moved it to `/var/lib/postgresql/18/docker` and declares `/var/lib/postgresql`
as the image's volume. If a manifest relies on the old default of
`/var/lib/postgresql/data` and mounts the PVC there, **the cluster is initialised
in the container's writable layer, outside the PVC** — it starts cleanly, works,
and is gone at the next pod restart. `PGDATA` is now set explicitly in all three
manifests and must stay that way.

### 3. `PGDATA` cannot be the mount root on a Longhorn volume

These are ext4 volumes, so the mount root contains `lost+found`, and `initdb`
refuses a non-empty directory. All three now use a subdirectory —
`/var/lib/postgresql/data/pgdata` with the PVC at `/var/lib/postgresql/data`.
The vaultwarden server previously kept its cluster *at* the root, which only
worked because that volume used to be `microk8s-hostpath` (no `lost+found`); it
would have failed the fresh `initdb` after the wipe.

### 4. `kubectl exec -i < dump` silently truncates

Piping the 2,354-line vaultwarden dump into `psql` through `kubectl exec -i`
stopped mid-`COPY`:

```
psql:<stdin>:865: ERROR:  missing data for column "password_history"
CONTEXT:  COPY ciphers, line 126: "98c1c0d8-..."
```

That is not a corrupt dump — the same file restored perfectly from *inside* the
pod. `kubectl exec` stdin is not a reliable bulk pipe. The 11 KB xboy dump went
through it fine, which is exactly what makes this dangerous: it works until the
input is big enough, and then it fails as what looks like data corruption.

```bash
kubectl -n <ns> cp dump.sql.gz <pod>:/tmp/dump.sql.gz
kubectl -n <ns> exec <pod> -- sh -c 'sha256sum /tmp/dump.sql.gz; gzip -t /tmp/dump.sql.gz'
kubectl -n <ns> exec <pod> -- sh -c \
  'gzip -dc /tmp/dump.sql.gz | psql -U "$POSTGRES_USER" -d postgres -f -'
kubectl -n <ns> exec <pod> -- rm -f /tmp/dump.sql.gz     # it holds password hashes
```

Compare the checksum after the copy, and count the log lines: the truncated
restore produced 132 of them, the complete one 223.

### 5. `RollingUpdate` on a ReadWriteOnce PVC deadlocks

Both xboy servers are Deployments with an RWO PVC and had the default strategy.
A rolling update cannot work there: the new pod cannot mount a volume the old pod
still holds, and the old pod is never terminated because the new one never becomes
ready. Both now carry `strategy: {type: Recreate}`. The StatefulSet does not need
this — it deletes the pod before creating its replacement.

### 6. ArgoCD `selfHeal` will undo the cutover, and re-do it too early

The xboy servers belong to `xboy-infrastructure-production`, which is `automated`
with `selfHeal: true` and `prune: true`. `automated` was removed from both xboy
Applications for the duration and the original policies saved to JSON first:

```json
{"automated":{"prune":true,"selfHeal":true}}
{"automated":{"prune":true,"selfHeal":true},"syncOptions":["ServerSideApply=true","RespectIgnoreDifferences=true"]}
```

Order matters on the way back: **commit and push the manifests first, then
re-enable `automated`.** Re-enabling it against the old commit is ArgoCD faithfully
putting `postgres:15-alpine` back on top of an 18 data directory — trap 1, but
inflicted by a controller instead of by hand. `kubectl diff` against the rendered
overlay came back empty before the patch, so the sync was a no-op on the
Deployments.

Note that these Applications are `applications.argoproj.io`. Plain
`kubectl patch app` resolves to `apps.catalog.cattle.io` on this cluster (a
leftover Rancher CRD) and fails with a confusing `NotFound`.

### 7. Vaultwarden resolves its database host once, at startup

Brought back up while the new server was still running `initdb`, the pod printed
its banner and then nothing — no `Rocket has launched`, no error, and it was
`1/1 Ready` the whole time because there is no readiness probe that touches the
database. `/proc/net/tcp` showed a `SYN_SENT` to the *previous* postgres pod IP:
`postgres` is a headless Service, so the name resolves to a pod IP, and that pod
had been replaced. Deleting the vaultwarden pod fixed it.

Start the database first, wait for `database system is ready to accept
connections`, and only then scale the consumer. Confirm with the log line, not
with pod readiness:

```
[start][INFO] Rocket has launched from http://0.0.0.0:80
```

## `postgres-root` had two Secrets with the same contents

Found while editing the manifests, and fixed in the same commit. The repo defined
`root-postgres-secret`, which the root app and the backup CronJob read, while the
live `postgres-root` Deployment read `postgres-root-secret` — a Secret that had
been created by hand and existed **only in the cluster**, never in git. They held
identical values, so nothing had broken yet; a single `kubectl edit` on either
would have broken the app or the backup with an auth error.

Both live Secrets were confirmed byte-identical (same sha256 over the sorted
`data`) before anything moved. Everything now reads the git-defined
`postgres-root-secret`; ArgoCD adopted it and pruned `root-postgres-secret`.

## Verification

The same query set ran against every server before and after, and the outputs were
diffed: extensions, roles (with `rolsuper`/`rolcanlogin`/`rolcreatedb` and whether
a password is set), schemas, **per-table row counts**, and sequences. Row counts
need one trick, because `count(*)` cannot be parameterised over a table list:

```sql
select table_schema||'.'||table_name||' '||
       (xpath('/row/c/text()',
              query_to_xml(format('select count(*) as c from %I.%I',
                                  table_schema, table_name), false, true, '')))[1]::text
from information_schema.tables
where table_schema not in ('pg_catalog','information_schema')
  and table_type='BASE TABLE' order by 1;
```

Capture it with `psql -At` both times, or the diff is all column headers and
padding. Results:

| Server | Tables | Spot checks | Diff |
|---|---|---|---|
| `postgres-root` | 5 | `projects 3`, `messages 2`, `earnings 2`, `receipts 2` | identical |
| `postgres-xboy` | 2 | `posts 28`, `post_views 184` | identical |
| `vaultwarden` | 29 | `ciphers 596`, `folders_ciphers 236`, `devices 25`, `users 3`, `__diesel_schema_migrations 46` | identical |

Also checked on each server: `select version()` reads 18.6, `show
data_checksums` reads `on`, encoding and collation are still `UTF8` /
`en_US.utf8` (a locale change would silently break index ordering), and
`VACUUM ANALYZE` was run because a restored database has no statistics.

End to end, after each cutover:

- `root-service` → HTTP 200, `blog-service` → HTTP 200 (both port **80**, not 3000)
- `vaultwarden` `/alive` → HTTP 200, which is a DB-backed endpoint, not a static one
- **all three backup CronJobs re-run against 18** and reported
  `UPLOAD_VERIFIED_OK` / `Backup completed successfully`. Worth doing explicitly:
  `pg_dump` refuses to run against a server newer than itself, so a backup image
  that lags the server fails *after* the upgrade, when the safety net is gone.
  `tools/s3-backup:2.0.0` already ships an 18.6 client, so nothing had to change.

The vaultwarden ingress (`password-manager-*.xboy.me` via traefik at
192.168.1.201) was **not** checked from outside: that address is on the wrong
subnet for this LAN, which is a pre-existing MetalLB pool problem noted in
[`2026-09-05-cluster-component-upgrades.md`](./2026-09-05-cluster-component-upgrades.md).
In-cluster and through the Service it is fine.

## Downtime

Per server, roughly the length of a pod restart plus the restore — under two
minutes for the two xboy servers, about four for vaultwarden including its own
pod restart. Consumers (`nextjs-root-app`, `nextjs-blog-app`, `vaultwarden`) were
scaled to zero for that window on purpose, so nothing wrote to a database that
was about to be replaced.
