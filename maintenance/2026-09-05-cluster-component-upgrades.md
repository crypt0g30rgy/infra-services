# In-cluster component upgrades — 2026-09-05

MetalLB, ArgoCD and KEDA upgraded; Longhorn checked and deliberately left alone.
Everything here was done against the live cluster (MicroK8s v1.35.6, snap
revision 9075, nodes `pi-5-16gb-srv-0` / `dell-amd64-srv`). Nothing was
restarted that did not need restarting, and no LoadBalancer address changed.

| Component | Before | After | How | Managed by |
|---|---|---|---|---|
| MetalLB | v0.15.2 | **v0.16.1** | upstream `metallb-native.yaml`, `kubectl apply` | MicroK8s `metallb` addon — **now diverged, see below** |
| ArgoCD | v3.4.3 | **v3.5.2** | upstream `install.yaml`, `kubectl apply` | nothing; plain manifests |
| ArgoCD dex | v2.45.0 | **v2.45.1** | came with `install.yaml` | as above |
| ArgoCD redis | 8.2.3-alpine | unchanged | already the version 3.5.2 ships | as above |
| KEDA | 2.20.1 | **2.20.2** | commit in the GitOps repo, ArgoCD synced it | ArgoCD `infrastructure-production` |
| Longhorn | v1.12.1 | **unchanged — already current** | — | Helm release `longhorn` |

Backups of every object touched were written to `/tmp/upgrade-backup-20260905/`
on the workstation, **not** into this repo: the ArgoCD dump contains
`argocd-secret` (admin hash, `server.secretkey`, the GitHub App private key in
the repo credentials). `/tmp` does not survive a reboot. Anything worth keeping
long-term has to be re-dumped somewhere private.

## MetalLB v0.15.2 → v0.16.1

```bash
kubectl apply -f https://raw.githubusercontent.com/metallb/metallb/v0.16.1/config/manifests/metallb-native.yaml
```

It is an in-place apply, not a reinstall, because every object name in the
upstream manifest already matches what was live — Deployment `controller`,
DaemonSet `speaker`, ConfigMap `metallb-excludel2`, Secret
`metallb-webhook-cert`, Service `metallb-webhook-service`,
ValidatingWebhookConfiguration `metallb-webhook-configuration`, ClusterRoles
`metallb-system:controller` and `:speaker`. **Both workload label selectors are
identical** (`app: metallb` + `component: controller`/`speaker`), which is the
one thing that has to match: selectors are immutable, and a mismatch turns the
upgrade into a delete-and-recreate that drops every advertised address. Check
that first, with `--dry-run=server`, before applying any future version.

The webhook Secret and the webhook `caBundle` are generated by the controller
and are absent from the upstream manifest, so the three-way merge leaves them
alone (`secret/metallb-webhook-cert unchanged`). The apply added one new CRD,
`configurationstates.metallb.io`.

### Verification

v0.16.1 ships that new CRD specifically to make the answer readable:

```
$ kubectl get configurationstates.metallb.io -A
NAMESPACE        NAME                      RESULT   ERRORSUMMARY
metallb-system   controller                Valid
metallb-system   speaker-dell-amd64-srv    Valid
metallb-system   speaker-pi-5-16gb-srv-0   Valid
```

and the two addresses survived unchanged:

| Service | IP |
|---|---|
| `ingress/traefik-external` | 192.168.1.201 |
| `portainer/portainer-agent` | 192.168.1.200 |

Both come from `ipaddresspool/default-addresspool`,
`["192.168.1.200-192.168.1.225"]`, advertised by
`l2advertisement/default-advertise-all-pools`.

Unrelated but still true: **that pool is on the wrong subnet.** The LAN is
192.168.0.x and the pool hands out 192.168.1.x, so those addresses are not
reachable from the LAN. The upgrade did not change that and did not fix it.

### This now diverges from the MicroK8s addon — read before touching it

`microk8s status` reports `core/metallb: enabled`, and the snap's copy is
pinned at **v0.15.2**:

```
/snap/microk8s/current/addons/core/addons/metallb/
├── crd.yaml          # v0.15.2 CRDs, no configurationstates
├── metallb.yaml      # controller/speaker v0.15.2
├── addresspool.yaml  # templates the pool from the range passed to `enable`
├── enable
└── disable
```

Consequences, in order of how much they can hurt:

- **`microk8s disable metallb` is destructive, not a downgrade.** Its `disable`
  script runs `kubectl delete -f crd.yaml` and `kubectl delete namespaces
  metallb-system`. Deleting the CRDs deletes `default-addresspool` and
  `default-advertise-all-pools` with them, so both LoadBalancer Services lose
  their addresses and the pool has to be recreated by hand (or by `enable` with
  the range passed again). It also leaves `configurationstates.metallb.io`
  behind, since that CRD is not in the snap's `crd.yaml`.
- **`microk8s enable metallb:<range>` puts v0.15.2 back**, silently, and
  rewrites the address pool from its template.
- **A `snap refresh` does not.** Addon manifests are applied only when an addon
  is enabled, so this upgrade survives snap refreshes. The risk is an explicit
  re-enable, not routine updates.

To go back to the snap's version deliberately, without deleting anything:

```bash
# on the arm64 node
sudo microk8s kubectl apply -f \
  /snap/microk8s/current/addons/core/addons/metallb/crd.yaml
sudo microk8s kubectl apply -f \
  /snap/microk8s/current/addons/core/addons/metallb/metallb.yaml   # {{allow_escalation}} needs substituting
```

The same argument applies to the other addon-managed components and is the
reason they were **not** upgraded here: `coredns` (1.10.1, upstream is 1.14.x),
`dashboard-metrics-scraper`, `metrics-server` and the `ingress` addon all come
from the snap. Hand-upgrading them buys a version number and loses the property
that `microk8s enable/disable` does what it says. MetalLB was worth the
exception — it is the only one of them where the running version is the thing
handing out addresses on the LAN — and the divergence is written down here
rather than discovered later.

## ArgoCD v3.4.3 → v3.5.2

Non-HA install (single `argocd-application-controller-0`, one replica of each
Deployment, `argocd-redis` rather than a redis-ha stack), so the upgrade is the
release's `manifests/install.yaml`. Two wrinkles made it not a single command.

**1. The ApplicationSet CRD no longer fits in a client-side apply.**

```
The CustomResourceDefinition "applicationsets.argoproj.io" is invalid:
metadata.annotations: Too long: may not be more than 262144 bytes
```

`kubectl apply` stores the whole object in the
`kubectl.kubernetes.io/last-applied-configuration` annotation, and that CRD is
now bigger than the 256 KiB annotation limit. Only that one object is affected,
so it was applied server-side and the rest client-side, keeping the existing
apply semantics everywhere else:

```bash
# 1. the one oversized CRD, server-side
kubectl apply --server-side --force-conflicts -f argocd-3.5.2-appsets-crd.yaml
# 2. everything else, unchanged semantics
kubectl apply -n argocd -f argocd-3.5.2-rest.yaml
```

Do not "fix" this by applying the whole file server-side. Migrating an existing
client-side-applied install to server-side apply hands field ownership over, and
fields that were set locally but are absent from upstream get pruned —
including the one below.

**2. `server.insecure` would have been wiped.** `argocd-cmd-params-cm` holds
`server.insecure: "true"` locally (traefik terminates TLS, argocd-server does
not), and that value *is* recorded in the ConfigMap's last-applied annotation.
Upstream ships the same ConfigMap with no `data:` at all, so a plain apply
deletes the key and the next `argocd-server` pod starts demanding TLS. It was
re-injected into the manifest before applying:

```yaml
# argocd-cmd-params-cm, added to the upstream manifest before apply
data:
  # Local: argocd-server runs without its own TLS; traefik terminates.
  # Not an upstream default - re-add after any manifest apply.
  server.insecure: "true"
```

**Re-check this on every future ArgoCD upgrade.** Verified afterwards:
`{"server.insecure":"true"}`.

Nothing else was at risk of being cleared. `argocd-cm`'s 3.4 contents were
exactly the upstream defaults (`resource.exclusions` and the
`ignoreResourceUpdates` set), so replacing them with 3.5's defaults is what
should happen. `argocd-secret` and `argocd-notifications-secret` carry a
last-applied annotation with an **empty** `data`, so the merge left their real
contents — admin password, `server.secretkey`, `webhook.github.secret`, the TLS
pair — untouched.

### Breaking changes in 3.5, and why none of them apply here

From the [3.4 → 3.5 upgrade notes](https://argo-cd.readthedocs.io/en/stable/operator-manual/upgrading/3.4-3.5/):

| Change | Applies here? |
|---|---|
| Helm 4.2.0: plain-HTTP OCI registries need `--insecure-oci-force-http` | No. Both configured repos are `type: git` over HTTPS; there is no Helm or OCI repo in ArgoCD. |
| UI extensions must externalise `react/jsx-runtime` (React 16 → 19) | No. No extensions configured in `argocd-cm`. |
| SSH `known_hosts` now used for repos without credentials (go-git 5.19) | No. Both repos are HTTPS **with** credentials (`gitops-private-repo` uses a GitHub App, `gitops-xboy-private-repo` a username/password). |
| GnuPG signature verification replaced by Source Integrity | No. Not used; legacy config would keep working anyway. |
| Event-listing gRPC methods return `EventList` | Only matters to API clients; nothing here calls it. |

All six pods on the new images and ready, and the four Applications still
present, still pointing at the same revisions, with sync policies intact:

| Application | Sync | Health |
|---|---|---|
| `apps-production` | Synced | Degraded — **pre-existing**, `apps/admin-svc` in CrashLoopBackOff (243 restarts over 20 h) |
| `infrastructure-production` | Synced | Degraded — **pre-existing**, `monitoring/prometheus` in CrashLoopBackOff on a full PVC |
| `xboy-apps-production` | Synced | Healthy |
| `xboy-infrastructure-production` | Synced | Healthy |

Neither Degraded roll-up is new, and neither is caused by the upgrade. Note also
that in 3.5 the `Application.status.resources[]` entries carry **no**
per-resource `health` field — all 74 resources of
`infrastructure-production` read `<none>`, as do the resources of the two
Healthy Applications. That is not a broken health check; the app-level roll-up is
computed from the controller's resource tree, so to find out *what* is degraded,
look at the pods in the Application's namespaces rather than at the CR.

One thing that looks wrong and is not: `argocd-applicationset-controller` has
**`replicas: 0`** and therefore no pod. That predates this upgrade — upstream
`install.yaml` sets no `replicas` field on that Deployment, so `apply` cannot
have changed it. Nothing in this cluster uses ApplicationSets.

## KEDA 2.20.1 → 2.20.2 — through git, not kubectl

KEDA's 7 objects belong to the ArgoCD Application `infrastructure-production`,
which is `automated` with **`selfHeal: true`** and **`prune: true`**. A
`kubectl apply` against the cluster is reverted on the next sync, and doing it
anyway is how you end up debugging a rollback you caused. The bump belongs in
the repo ArgoCD reads:

```
repo:   github.com/tesseractdigitainnovations/k8s-infra
path:   infrastructure/overlays/production  ->  ../../base  ->  base/keda
commit: 45ac84f  "keda: 2.20.1 -> 2.20.2"
```

The repo vendors the whole release manifest, so the change is a file swap plus
one line in `infrastructure/base/keda/kustomization.yaml`. The previous vendored
copy had been passed through a YAML formatter (long CRD `description` strings
rewrapped, quoting changed), which makes a diff against upstream noisy; a
word-level diff of the old file against upstream v2.20.1 confirmed there were no
local edits, so it was replaced with untouched upstream v2.20.2 output. The next
bump is now a clean file swap.

ArgoCD picked the commit up on its own (`revision: 45ac84f`) and rolled both
Deployments. Note the overlay's `pin-to-pi-node` component: **KEDA runs on the
arm64 node**, so the rollout needs headroom there — 100m CPU / 100Mi per pod,
against roughly 390m and 1.6 GiB free. It fits, but only just.

## Longhorn — nothing to upgrade

v1.12.1 is **the current release** (published 2026-08-14), and it is what is
installed: Helm release `longhorn` revision 4, chart `longhorn-1.12.1`,
`longhorn-manager:v1.12.1`, and the `current-longhorn-version` setting reads
`v1.12.1`. There is no upgrade to do, and this is worth re-checking rather than
assuming, because the image scanner reports something that looks like one:

> `docker.io/longhornio/csi-provisioner:v5.3.0` → `v6.3.0`

**Do not bump that tag.** The CSI sidecars (`csi-provisioner`, `csi-attacher`,
`csi-resizer`, `csi-snapshotter`, `livenessprobe`) are pinned by
`longhorn-manager` itself, which deploys them; their versions are chosen per
Longhorn release and are not independent knobs. Editing the Deployment is
reverted by the manager, and pinning a newer sidecar than the release was tested
against is how CSI stops provisioning. The same applies to
`longhorn-instance-manager` and `longhorn-engine`. The only supported way to
move any of them is a Longhorn release upgrade.

For whenever v1.13 does land, the shape of that job:

1. `helm upgrade` swaps the manager, UI, driver deployer and instance managers.
   This part is non-disruptive to running workloads — the engine processes for
   attached volumes live inside the existing `instance-manager` pods.
2. The disruptive part is the **per-volume engine upgrade**, which needs each
   volume either detached or live-upgradable. There is exactly one engine image
   in use today, `ei-493e04e7` (`longhorn-engine:v1.12.1`), with refCount 64.
3. A degraded volume must not be engine-upgraded. Which brings us to:

### The real prerequisite: two degraded volumes, and why

```
monitoring/prometheus-data  (5Gi)  attached  degraded
monitoring/loki-data        (5Gi)  attached  degraded
  Scheduled: "precheck new replica failed: insufficient storage"
```

Both want 2 replicas and have 1, on `dell-amd64-srv`. The message is accurate
and the arithmetic is worth writing down, because "insufficient storage" reads
like a full disk and the disk is not full:

| | max | reserved | scheduled | schedulable budget | free budget |
|---|---|---|---|---|---|
| `dell-amd64-srv` | 465.5 GiB | 139.6 GiB | 144.0 GiB | 325.8 GiB | **181.8 GiB** |
| `pi-5-16gb-srv-0` | 114.7 GiB | 60.0 GiB | 54.0 GiB | 54.7 GiB | **0.7 GiB** |

With `storage-over-provisioning-percentage: 100`, a disk can only be scheduled
up to `maximum - reserved`. The arm64 node's disk — the **SD card** — has 60 GiB
of its 114.7 GiB reserved and 54.0 GiB already scheduled, leaving 0.7 GiB. A
5 GiB replica does not fit. And `replica-soft-anti-affinity: false` correctly
refuses to put the second replica on the same node as the first, so there is
nowhere for it to go. The volumes are not broken; the cluster has exactly one
node with room on it.

Options, best first:

1. **Give the arm64 node a real disk** (USB SSD as a second Longhorn disk) and
   stop putting replicas on an SD card at all. This is the same conclusion the
   node-hardening work reached for the dqlite datastore — see
   [`../incidents/2026-09-05-node-hardening.md`](../incidents/2026-09-05-node-hardening.md).
2. **Reclaim scheduling budget on that disk**: the 60 GiB reservation is over
   half the card, and two orphaned 40 GiB `jenkins/buildkit-cache-pvc` volumes
   are still on the books. Deleting the orphans and moving that cache to
   `local-path` frees real space.
3. Drop these two volumes to `numberOfReplicas: 1` and admit they are
   single-copy. Honest, and appropriate for a Prometheus TSDB and a Loki store
   that are already broken for other reasons (prometheus is 0/1 with a full PVC,
   loki's data is corrupt), but it is a decision, not a fix.
4. `replica-soft-anti-affinity: true` — makes the warning go away by putting
   both replicas on one node. Not a fix; it buys nothing but a green dashboard.

Also still true and unrelated to any upgrade: the Longhorn **backup target is
empty**, so none of this is recoverable off-cluster. `minio-s3` already runs on
the arm64 node.

## Found while doing this: the arm64 node re-pulls images it already had

The KEDA rollout took **10m2s to pull an 84 MB image** (≈140 KB/s). The link is
100 Mbps, so the link is not the explanation. This is:

```
image_gc_manager.go:394 Disk usage on image filesystem is over the high threshold,
  trying to free bytes down to the low threshold usage=71 highThreshold=70
  amountToFree=13000178892 lowThreshold=60
kubelet.go:1657 "Image garbage collection failed multiple times in a row"
  err="Insufficient free disk space on the node's image filesystem (71% of 114.7 GiB
  used). Failed to free sufficient space by deleting unused images (freed 0 bytes)."
```

MicroK8s ships `--image-gc-high-threshold=70 --image-gc-low-threshold=60` (both
predate the node-hardening change; they are in the snap's default kubelet args).
The SD card sits at 70–71 % used, so **the kubelet is permanently above the high
threshold**: every five minutes it tries to free 13 GB by deleting images,
deletes whatever is not currently referenced, gets nowhere, and logs an error.
The cost is not the log line — it is that images get evicted and then re-pulled
over a slow link on the next rollout, on an SD card that is also serving
Longhorn replicas and the API server's dqlite.

It cannot succeed, because the space is not images:

| path | size |
|---|---|
| `/var/lib/docker` | 29 GiB (compose stacks; `docker system df` says only ~1.2 GiB is reclaimable) |
| `/var/snap/microk8s/common/var/lib/containerd` | 19 GiB |
| `/home/w3b` | 20 GiB |
| `/var/lib/longhorn` | 5.9 GiB actual (54 GiB *scheduled* — replicas are sparse) |
| `/var/log` | 2.5 GiB |
| **total** | **77 GiB of 115 GiB** |

Getting to the 60 % low threshold means freeing 13 GB that image GC cannot
touch. Two ways out, neither applied here — both are node changes rather than
component upgrades, and neither was in scope for this round:

1. **Raise the thresholds** to something achievable on this node
   (`--image-gc-high-threshold=85 --image-gc-low-threshold=75` in
   `/var/snap/microk8s/current/args/kubelet`, then
   `sudo snap restart microk8s.daemon-kubelite`). Stops the five-minute retry
   loop and stops evicting images that are about to be needed again. Note the
   kubelet's own `imagefs.available<2Gi` eviction threshold still protects the
   node — there are 34 GiB free, so this is not the same as turning GC off.
2. **Move the load off the card**: Docker's data root and `/home/w3b` are 49 GiB
   between them on the same SD card as the container store, the dqlite datastore
   and the Longhorn replicas. This is the same conclusion as
   [`../incidents/2026-09-05-node-hardening.md`](../incidents/2026-09-05-node-hardening.md)
   reached from the memory side, and the same conclusion the degraded-volume
   arithmetic above reaches from the storage side.

## Notes for the next time

- **Image pulls dominate the wall-clock.** The amd64 node is on Wi-Fi and the
  arm64 node's link is stuck at 100 Mbps; a 210 MB `argocd` layer took 3m23s,
  and see above for the 84 MB one that took ten minutes. Pods sit in `Pending`
  while pulling, which looks like a scheduling failure and is not —
  `kubectl describe pod` showing `Pulling` is the tell. Expect a four-component
  upgrade to take 20+ minutes of waiting.
- **Always `--dry-run=server` first.** It caught the CRD annotation limit and
  confirmed the MetalLB selectors before anything was changed.
- **Check who owns an object before upgrading it**: an ArgoCD Application with
  `selfHeal`, a MicroK8s addon, a Helm release, or nobody. Each one implies a
  different upgrade path, and three of the four components here fell into a
  different category.
- Watch node headroom during rollouts. Both nodes carry reservations now, so a
  rolling update that needs a surge pod can genuinely fail to schedule — the
  arm64 node has ~390m CPU spare.
